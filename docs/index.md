## Repo in one paragraph

The bot is a dry-run Solana alpha research loop. It watches configured wallets, parses recent swap transactions, looks for multiple wallets buying the same mint in a short window, scores the mint using read-only market and holder data, opens a simulated position only when the score clears gates, and feeds paper outcomes back into wallet trust/tiering. The intended output is evidence about wallets and signals, not live execution.

## Safety principles

- `DRY_RUN=true` is required. The config loader rejects `DRY_RUN=false`.
- No wallet private keys are configured or needed.
- No swap execution path exists in v1.
- The dashboard is read-only and local-state-only.
- Telegram alerts and reports are notifications, not order instructions.
- Secrets must stay in `.env` or external service configuration, never in committed files or documentation.
- Any future live-trading work needs a separate explicit approval boundary and its own design review.

## Generated/runtime data

These paths are expected to change during normal operation:

- `data/memecoin-alpha.sqlite` and SQLite WAL/SHM sidecars.
- `data/*report*.json` generated by discovery/vetting.
- `config/cielo-wallet-candidates.json` when Cielo discovery runs.
- `config/watched-wallets.json` when a human adds wallets or wallet maintenance applies rotation/candidate sync.
- `config/.wallet-backups/` backup snapshots, when wallet-maintenance writes changes.

The active watchlist is operational state. Treat it carefully and inspect diffs before committing.

## Current deployed posture

The known local deployment shape is:

- Raspberry Pi host.
- Node.js >= 22.
- User systemd services under `~/.config/systemd/user/`.
- Scanner service runs dry-run from this repo.
- Dashboard service serves a LAN read-only dashboard on port 8788 when configured.
- Hermes cron jobs supervise health, paper-position staleness, and periodic wallet sourcing/maintenance.

See `operations.md` for exact commands and runbooks.
